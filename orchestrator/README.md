# Оркестратор: последовательная очередь задач для CLI-агентов

Автономный модуль для любого Git-проекта: из длинного файла очереди задачи
выполняются по одной — CLI-агент (Codex CLI или OpenCode) получает задание,
запускается обязательный gate, при успехе коммит делается автоматически,
результат пишется в журнал. Внешних Python-пакетов нет; всё состояние —
обычные файлы внутри одного каталога `orchestrator/`.

Принцип: оркестратор управляет только процессом (очередь, gate, Git, журнал),
качество работы определяют постановка задачи, правила проекта (`AGENTS.md`
целевого проекта) и команды gate.

## Установка в проект

1. Скопируйте каталог `orchestrator/` в корень вашего Git-проекта и сохраните
   его коммитом. Все пути в конфигурации отсчитываются от корня проекта;
   каталог может называться иначе (путь задаётся в `config.json`).
2. Требования: Linux/macOS/WSL, Bash, Python 3.10+, Git и один авторизованный
   CLI-агент: `codex` (Codex CLI) или `opencode` (OpenCode CLI).
3. Заполните `orchestrator/config.json`: бэкенд, модели, профили проверок.
   Образец — `orchestrator/examples/config.example.json`; скопируйте его
   и заполните под свой проект (неизвестные ключи отклоняются).
4. Добавьте согласованные задачи в `orchestrator/TASKS.md`. Единственный
   образец — `orchestrator/examples/TASKS.md`; он не входит в рабочую очередь.
5. Проверьте план и запустите. Команды выполняются **из корня проекта**:

```bash
codex --version            # или: opencode --version
git add -- orchestrator/
git commit -m "orchestrator: add task queue"
bash orchestrator/run.sh --dry-run
bash orchestrator/run.sh
```

По умолчанию работа идёт в ветке `auto/tasks`, push включён и требует
настроенного remote `origin`. Для локальной работы без remote используйте
`--no-push`. Если Git ещё не настроен, сначала инициализируйте репозиторий,
задайте `user.name` / `user.email` и создайте начальный коммит проекта.

| Путь внутри `orchestrator/` | Назначение |
|---|---|
| `run.sh` | Точка входа: очередь задач или проверки через `--check` |
| `orchestrator.py` | Выполнение очереди |
| `checks.py` | Резолвер профилей `--check` (встроенный `orchestrator` + ключ `checks` из конфига) |
| `config.json` | Бэкенд, модели, проверки, Git, таймауты и пути |
| `TASKS.md` | Текущая очередь; изначально пуста |
| `PROGRESS.md` | Журнал и состояние; создаётся при первом завершении задачи |
| `.runtime/logs/` | Локальные логи; создаются при запуске и не коммитятся |
| `tests/` | Автоматические проверки с заглушками агентов |
| `examples/` | Примеры задач и настроек; автоматически не выполняются |
| `VALIDATION.md` | Результаты проверки модуля |

Служебные файлы модуля защищены от правок агентом: задачи, журнал, конфиг,
`orchestrator.py`, `run.sh` и `checks.py` проверяются по контрольным суммам.
Задания агентам должны целить файлы вне `orchestrator/`.

## Бэкенды

Ключ `backend` в `config.json` выбирает агента: `"codex"` (по умолчанию)
или `"opencode"`. На один запуск бэкенд можно переключить флагом
`--backend codex|opencode` — он перекрывает конфиг; отдельный конфиг-файл
для этого не нужен, секции моделей обоих бэкендов живут в одном конфиге.
Для обоих промпт подаётся через stdin; использованная
настройка — только из `config.json`, переменные окружения не читаются.

| | Codex | OpenCode |
|---|---|---|
| Команда | `codex exec [--model …] -c model_reasoning_effort=… --sandbox … -` | `opencode run --agent build --format json [--model …]` |
| Финальный ответ | `--output-last-message` | Поле `part.text` последнего text-event потока `--format json` |
| Права на файлы | `sandbox` из конфига (`read-only`/`workspace-write`/`danger-full-access`) | `permissions` в `opencode.json` целевого проекта; оркестратор не передаёт ни песочницу, ни `--auto` |
| Модели | секция `models.codex` | секция `models.opencode` |
| Настройка reasoning | ключи `efforts` | суффикс `#variant` в строке модели; ключ `efforts` игнорируется с предупреждением |

Имя/путь CLI переопределяются ключами `codex_bin` / `opencode_bin`.
Пустая строка модели для tier означает «модель из настроек самого CLI».
Плоский формат `models: {"light": …}` сохранён для совместимости старых
конфигов и допустим только при `backend="codex"`.

## Повседневная работа

1. Добавьте задачи в `orchestrator/TASKS.md`. В пределах текущего журнала
   используйте новые ID; для новой пачки выполните сброс, описанный ниже.
2. Сохраните изменения очереди коммитом.
3. Выполните `bash orchestrator/run.sh` из корня проекта.
4. Просмотрите изменения и журнал `orchestrator/PROGRESS.md`.

Выполненные задачи пропускаются, новые запускаются по порядку секций.
Пустой `TASKS.md` допустим: оркестратор сообщает, что работы нет.

```bash
bash orchestrator/run.sh --list             # ID, модель, сложность, статус
bash orchestrator/run.sh --dry-run          # также команды gate и число повторов
bash orchestrator/run.sh --only DOC-1       # только эта задача
bash orchestrator/run.sh --from FIX-2       # с этой секции до конца
bash orchestrator/run.sh                    # вся невыполненная очередь
bash orchestrator/run.sh --push             # явно включить push после каждого коммита
bash orchestrator/run.sh --no-push          # явно отключить push на этот запуск
bash orchestrator/run.sh --check full       # только проверки проекта
bash orchestrator/run.sh --help             # справка по очереди и проверкам
```

`--only`, `--from` и `--mark-done` взаимоисключающие; неизвестный ID — ошибка.
`--from` и `--only` не проверяют зависимости: выбор точки старта — решение
пользователя. `--list` и `--dry-run` не запускают агента, gate и Git-записи;
они работают и без `git init`.

## Формат TASKS.md

````markdown
# Очередь

## DOC-1: Описать запуск проекта
tier: light
gate: bash orchestrator/run.sh --check full
retries: 1
```prompt
Создай docs/QUICKSTART.md с точными командами установки и запуска этого проекта.
Команды возьми из существующих конфигурационных файлов и документации.
Не меняй код приложения.
```

## FIX-2: Исправить обработку пустого ввода
tier: standard
gate: bash orchestrator/run.sh --check full
retries: 1
```prompt
Здесь опиши конкретную ошибку, ожидаемое поведение и критерии готовности.
При необходимости добавь к полному гейту дополнительные проверки по типу правки.
```
````

| Элемент | Правило |
|---|---|
| Заголовок | `## ID: Название`; ID начинается с латинской буквы, затем буквы/цифры/`_`/`-` |
| Порядок | Как в файле; алфавитная/числовая сортировка не применяется |
| `tier` | `light`, `standard`, `heavy`; если отсутствует — `standard` |
| `gate` | Обязательная однострочная shell-команда или точное значение `skip` |
| `retries` | Число исправлений после провала gate, 0–20; по умолчанию 1 |
| `prompt` | Один непустой блок с оградой из трёх или более обратных кавычек либо тильд |

Метаданные должны стоять перед блоком prompt. Повтор ID/поля, неизвестное
поле, незакрытый или пустой prompt останавливают запуск **до обращения
к агенту**. Заголовки внутри prompt считаются его текстом; для вложенных
блоков кода используйте внешнюю ограду из четырёх кавычек или `~~~prompt`.
Русский текст, эмодзи, UTF-8 BOM и переводы строк CRLF поддерживаются.

Примеры заданий — `examples/TASKS.md`; чтобы выполнить, перенесите
согласованную секцию в рабочую очередь `orchestrator/TASKS.md`.

## Проверки (`--check`)

Режим `--check` запускает только проверки проекта и не работает с очередью:
не читает задачи, не требует чистого рабочего дерева, не захватывает
блокировку очереди и не выполняет Git-операции. Его можно вызывать и вручную
из любого каталога, и изнутри уже запущенного оркестратора. Режим проверок
отключает запись Python-байткода (`PYTHONDONTWRITEBYTECODE=1`), в том числе
в дочерних процессах: иначе вложенный Python-гейт создавал бы `__pycache__`
внутри защищённого каталога и останавливал очередь.

Профили задаются в `config.json` ключом `checks` — словарь «профиль → массив
shell-команд». Команды выполняются по очереди **из корня проекта**; ошибка
любой останавливает профиль с её кодом возврата:

```json
"checks": {
  "full": [
    "python3 -m unittest discover -s orchestrator/tests",
    "npm test"
  ],
  "lint": [
    "npx eslint ."
  ]
}
```

Встроен ровно один профиль: `orchestrator` (самопроверка модуля:
`python3 -m unittest discover -s orchestrator/tests`); переопределить его
в конфиге нельзя. Профиль с именем `full` — по умолчанию для `--check`
без аргумента: задайте его в `checks` под этим именем. `--check --help`
печатает актуальный список профилей динамически. Неизвестный или пустой
профиль — ошибка (код 2) без выполнения команд.

Гейт каждой задачи обычно ссылается на профиль:

```text
gate: bash orchestrator/run.sh --check full
```

Дополнительные проверки по типу правки добавляйте явно в `gate`:

```text
gate: bash orchestrator/run.sh --check full && bash orchestrator/run.sh --check lint
```

Отсутствующие инструменты (SDK, JDK, компилятор и т.п.) не считаются успехом:
команда завершится ошибкой, и задача не будет засчитана. Не заменяйте
обязательный gate на `skip`; значение `skip` поддержано только для неигровых
вспомогательных задач и явно пишется в журнал как **ПРОПУЩЕНА**.

Без настройки `gate_base` команда gate выполняется на хосте через `sh -c`
в корне проекта. Для Docker задайте в `config.json`:

```json
"gate_base": ["docker", "compose", "run", "--rm", "app"]
```

Тогда `gate: npm test` превратится в `docker compose run --rm app sh -c 'npm test'`.
Весь массив `gate_base` — аргументы команды, а не строка shell: конвейеры,
перенаправления и `&&` пишите в `gate`, а не в `gate_base`. Проверка
выполняется с правами пользователя на хосте — это удобно для Docker, даже
если агент не может его запустить внутри своей песочницы.

При провале gate агент получает исходную задачу, предыдущий ответ и конец
лога; его уже сделанные правки сохраняются. Используется новый запуск агента
с той же моделью. После `retries` исправлений цикл останавливается. Ошибка
запуска агента, неуспешный код выхода, пустой итог, таймаут агента/gate и
сбой push допускают до `restart_retries` повторов с паузой `retry_delay`;
этот бюджет отделён от исправлений проваленного gate. Строка `BLOCKED:`
останавливает очередь без повтора. Ни ошибка тестов, ни отсутствующий SDK,
ни ручной аудит не превращаются в успех.

## Конфигурация

Редактируйте `orchestrator/config.json`; неизвестные ключи отклоняются.
Другой файл можно передать как `--config path/to/config.json`; он должен
находиться внутри проекта и быть добавлен в Git. Файл может задавать только
отличия от значений по умолчанию: например, конфиг `{"backend": "opencode"}`
включает бэкенд OpenCode поверх остальных настроек по умолчанию; для смены
бэкенда обычно достаточно флага `--backend`.
Приоритет настроек: флаги командной строки → `config.json` → значения
по умолчанию. Переменные окружения не читаются (см. миграцию ниже).

| Ключ | По умолчанию | Назначение |
|---|---|---|
| `backend` | `codex` | Бэкенд агента: `codex` или `opencode` |
| `tasks_file` | `orchestrator/TASKS.md` | Очередь, путь относительно корня |
| `progress_file` | `orchestrator/PROGRESS.md` | Журнал и состояние завершённых задач |
| `branch` | `auto/tasks` | Локальная ветка для работы |
| `remote` | `origin` | Remote для необязательного push |
| `push` | `true` | Выполнять push после каждой завершённой задачи |
| `codex_bin` / `opencode_bin` | `codex` / `opencode` | Имя программы или путь к CLI |
| `sandbox` | `workspace-write` | Песочница агента Codex (для opencode не используется) |
| `gate_base` | `[]` | Префикс команды проверки массивом аргументов |
| `checks` | `{}` | Профили `--check`: «профиль → массив shell-команд» |
| `task_timeout` | `3600` | Секунд на один запуск агента |
| `gate_timeout` | `1800` | Секунд на один запуск gate |
| `git_timeout` | `120` | Секунд на commit и на push |
| `restart_retries` | `3` | Дополнительные запуски после сбоя агента, пустого ответа, таймаута или сбоя push; 0–20 |
| `retry_delay` | `30` | Пауза между перезапусками, секунд |
| `models` | см. ниже | Модели по tier, вложенно: секции `codex` и `opencode` |
| `efforts` | `low` / `medium` / `high` | Усилие Codex для light / standard / heavy |

В `models` используйте ключи `light`, `standard`, `heavy` внутри секции
активного бэкенда; выберите модели, доступные вашему аккаунту. Пустая строка
переключает tier на модель из настроек самого CLI.

### Миграция со слоя переменных окружения

Ранние версии модуля читали настройки из окружения. Слой удалён: окружение
больше не читается, даже если переменные заданы. Перенесите значения
в `config.json`:

| Прежняя переменная | Ключ `config.json` |
|---|---|
| `MODEL_LIGHT` / `MODEL_STANDARD` / `MODEL_HEAVY` | `models.codex.light` / `.standard` / `.heavy` (или `models.opencode.*`) |
| `EFFORT_LIGHT` / `EFFORT_STANDARD` / `EFFORT_HEAVY` | `efforts.light` / `.standard` / `.heavy` |
| `CODEX_BIN` | `codex_bin` |
| `SANDBOX` | `sandbox` |
| `TASKS_FILE` / `PROGRESS_FILE` | `tasks_file` / `progress_file` |
| `BRANCH` / `REMOTE` | `branch` / `remote` |
| `NO_PUSH=0/1` | `push: true/false` (или флаг `--push/--no-push`) |
| `GATE_BASE='docker compose run --rm app'` | `gate_base: ["docker", "compose", "run", "--rm", "app"]` |
| `TASK_TIMEOUT` / `GATE_TIMEOUT` / `GIT_TIMEOUT` | `task_timeout` / `gate_timeout` / `git_timeout` |
| `RESTART_RETRIES` / `RETRY_DELAY` | `restart_retries` / `retry_delay` |
| встроенные профили `--check` | ключ `checks` (профили проекта переносятся один в один) |

Пути всегда отсчитываются от корня проекта; пути с пробелами поддерживаются.
Ограничение формата: задачи, конфигурация и журнал — обычные пути без symlink
и `..`. Другой конфиг задаётся флагом `--config`, а не окружением.

## Новая пачка задач: очистить и заполнить заново

После завершения предыдущей пачки остановите все запуски оркестратора
и убедитесь, что нужные правки проекта сохранены в коммитах. Из корня проекта:

```bash
printf '# Задачи\n\n' > orchestrator/TASKS.md
rm -f orchestrator/PROGRESS.md
```

Это полностью очищает очередь и удаляет журнал завершения; архивы и копии
не создаются. Запишите новые задачи — ID можно снова начинать с `P1`, `P2`,
поскольку прежнего журнала больше нет. Сохраните подготовку и запустите пачку:

```bash
git add -A -- orchestrator/
git commit -m "orchestrator: replace task queue with a new batch"
bash orchestrator/run.sh --dry-run
bash orchestrator/run.sh
```

Без удаления старого журнала неизменённые задачи с прежними ID будут
пропущены, а изменённые задачи с теми же ID остановят запуск из-за
несовпадения fingerprint. Очистка не откатывает код и не удаляет Git-коммиты
предыдущей пачки — только список задач и учёт их завершения. Локальные логи
можно оставить либо удалить отдельно из `orchestrator/.runtime/`.

Обычно новую пачку запускают в текущей ветке задач. Для отдельной ветки
запишите свободное имя в ключ `branch` конфига (или используйте отдельный
`--config`) и продолжайте с тем же значением:

Если ветка уже существует, сначала выберите её вручную: `git switch …`.

## Git и журнал

- Стартуйте из корня Git-проекта с начальным коммитом, заданными
  именем/email и чистым рабочим деревом. Для возобновления своей
  незавершённой задачи допустимы её сохранённые правки при наличии
  контрольной точки.
- Скрипт создаёт `auto/tasks` от текущего HEAD. Если такая ветка уже
  существует, выберите её вручную; автоматического перехода нет. Ветки
  `main` и `master` для выполнения отклоняются.
- Для каждой завершённой задачи коммитятся все видимые Git-изменения вместе
  с записью журнала. Отсутствие правок кода допустимо: задача может
  закончиться коммитом только журнала.
- Строки `<!-- orchestrator:v1 ... -->` в `PROGRESS.md` — служебные записи
  с ID, fingerprint, итогом и результатом gate; не редактируйте их вручную.
  Человекочитаемый текст журнала можно дополнять обычными абзацами.
- Повторный запуск пропускает выполненные ID. Изменение содержания
  завершённой задачи под прежним ID вызывает ошибку: создайте новую секцию
  с новым ID. Старые завершённые секции можно удалять из очереди — записи
  журнала сохраняются.
- После редактирования очереди сохраните её коммитом и снова запустите
  скрипт. Не редактируйте очередь, конфигурацию или проект одновременно
  с выполнением.
- `orchestrator/.runtime/` хранит логи каждого запуска и исключается локально
  через Git info/exclude: менять корневой `.gitignore` проекта не требуется.
  Linked worktrees поддерживаются.
- Файловая блокировка на общий Git-репозиторий не даёт стартовать второму
  оркестратору, даже в другом linked worktree.
- Push включён по умолчанию (`push: true`); `--no-push` отключает его на один
  запуск. При провале push локальный коммит сохраняется, следующие задачи
  не запускаются. Исправьте доступ, выполните `git push` вручную, затем
  продолжите обычным запуском: сохранённый в контрольной точке push будет
  повторён до следующей задачи.

## Если выполнение остановилось

Перед запуском агента сохраняется атомарная локальная контрольная точка
`orchestrator/.runtime/checkpoint.json`: задача и её fingerprint, ветка,
исходный HEAD, снимок защищённых файлов, текущий этап и счётчики запусков.
Данные агента и незавершённые правки остаются на месте; reset, clean и stash
не выполняются. Контрольная точка не коммитится и удаляется после завершения
задачи и push (либо явного `--no-push`). Завершённые задачи определяются
по закоммиченному журналу.

После внешнего прерывания достаточно повторить обычный запуск
(`bash orchestrator/run.sh`). Оркестратор продолжит незавершённую задачу,
даже если в ней остались новые или изменённые файлы: агент получит исходное
задание, последние итоги, ответ и лог, а также указание изучить и сохранить
полезные правки. Сбой во время gate возобновляет проверку без нового вызова
агента. При остановке во время коммита повторяются gate и коммит; если
коммит уже состоялся, он проверяется по родителю, дереву Git и журналу
и не создаётся повторно. Прерванный push повторяется отдельно. Ошибки commit
hook после устранения причины также восстанавливаются обычным запуском.

Сбой агента, пустой ответ, таймаут и push сначала повторяются в текущем
процессе. Если CLI сообщает `try again at ...`, пауза увеличивается до
указанного времени сброса лимита (локальный часовой пояс машины). Иначе
используется `retry_delay`. После исчерпания повторов правки и контрольная
точка сохраняются; новый запуск начинает новый бюджет перезапусков.
Ctrl+C/SIGTERM во время ожидания прекращают работу, а не запускают новый
повтор. Отдельная системная служба не устанавливается.

Логи продолжаются в `orchestrator/.runtime/logs/<UTC-время>/`:
`ID.exec.N.log`, `ID.gate.N.log`, `ID.last.md`, `ID.commit.N.log`,
`ID.push.N.log`. Новые попытки получают новые номера и не затирают логи
прошлых запусков.

Автовозобновление требует ту же задачу, ветку, HEAD и неизменные защищённые
файлы. Другая задача через `--only`/`--from`, изменённый fingerprint,
незнакомый коммит, повреждённая контрольная точка и изменения защищённых
путей останавливают запуск. Сторонние правки в чистом ранее проекте без
контрольной точки не подхватываются. Не редактируйте проект параллельно
активной задаче: её сохранившиеся правки будут переданы агенту и войдут
в коммит после успешного gate.

При `BLOCKED:` сначала нужно решение владельца. Для проверенного ручного
исправления остаётся команда **в ветке задач**:

```bash
bash orchestrator/run.sh --mark-done FIX-2
```

Она снова запускает gate и при успехе коммитит **все текущие изменения**
вместе с журналом, без вызова агента. Используйте её только для разобранных
изменений этой задачи.

Если изменены защищённые файлы, сначала восстановите их из коммита, сохранив
нужные правки проекта отдельно. Без собственной контрольной точки оркестратор
откажется использовать незакоммиченный журнал как подтверждение завершения.

Ctrl+C, SIGTERM и таймаут останавливают активную группу процессов агента/gate.
Дочерний процесс наследует блокировку: пока оставшийся агент или gate ещё
работает, второй оркестратор откажется запускаться; после его завершения
обычный запуск восстановится из контрольной точки. Коды завершения: `0` —
очередь/выбор выполнены или работы нет, `1` — ошибка выполнения или данных,
`2` — ошибка аргументов командной строки, `130` — Ctrl+C вне активного
процесса.

## Границы автоматизации

Проверки контрольных сумм и Git-ветки обнаруживают случайную правку
служебных файлов, но не являются изоляцией от враждебного агента.
Просматривайте diff и историю перед слиянием. Gate — доверенная команда
пользователя; она выполняется с правами хостового пользователя. Права
агента определяются выбранной песочницей (Codex: `sandbox`; OpenCode:
`permissions` в `opencode.json` проекта); полный доступ используйте только
в подходящей изолированной среде. Настройки доверия и hooks самого CLI
остаются действующими.

Оркестратор не запускает субагентов, не выполняет merge/deploy и не
исправляет Git-конфликты автоматически. Следуйте `AGENTS.md` целевого
проекта; `examples/AGENTS.md` — необязательный шаблон для объединения
с вашими правилами.

Используемые CLI-флаги сверены с `codex-cli 0.167.0-alpha.4` (`codex exec
--help`) и `opencode run` (поток `--format json`). Запуски с настоящими
моделями в проверку комплекта не входили; пример живого прогона —
`VALIDATION.md`.

## Самопроверка модуля

```bash
bash orchestrator/run.sh --check orchestrator
```

Эквивалентно `python3 -m unittest discover -s orchestrator/tests`.
Тесты создают временные Git-репозитории и подменяют агентов заглушками;
аккаунт, API-ключ и сеть для них не нужны. Сводка реальных прогонов —
в `VALIDATION.md`.
