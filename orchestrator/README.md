# Оркестратор проекта «Составь слова»


Комплект находится в каталоге `orchestrator/`: программа, настройки,
очередь, журнал, документация, тесты и локальные логи. Файлы автоматизатора в корне
основного проекта создавать не требуется. Правила проекта задаёт корневой
`AGENTS.md`; оркестратор работает только в инфраструктуре разработки.

## Установка и первый запуск

1. Каталог уже включён в проект. Настройки находятся в `orchestrator/config.json`.
2. Нужны Linux/macOS/WSL, Bash, Python 3.10+, Git и авторизованный Codex CLI.
   Внешних Python-пакетов нет. Для Gradle нужны JDK 21 и Android SDK 36;
   используйте `JAVA_HOME`, `local.properties` или `ANDROID_HOME` как при обычной сборке.
3. Добавьте согласованные задачи в пустой `orchestrator/TASKS.md`.
   Единственный образец — `orchestrator/examples/TASKS.md`; он не входит в рабочую очередь.
4. Сохраните комплект коммитом и проверьте план. Все команды ниже выполняются
   **из корня основного проекта**:

```bash
codex --version
codex login
git add -- orchestrator/
git commit -m "orchestrator: добавить очередь задач"
bash orchestrator/run.sh --dry-run
bash orchestrator/run.sh
```

По умолчанию используется ветка `auto/tasks`, push включён и требует настроенного
remote `origin`. Для локальной работы без remote используйте `--no-push`.
После добавления задачи, например `DOC-1`, можно выполнить только её:

```bash
bash orchestrator/run.sh --only DOC-1
```

Если `auto/tasks` уже существует, перед запуском выберите её командой
`git switch auto/tasks` либо задайте новую ветку через `BRANCH`.
Если Git ещё не настроен, сначала инициализируйте репозиторий, задайте
`user.name` / `user.email` и создайте начальный коммит проекта.

| Путь внутри `orchestrator/` | Назначение |
|---|---|
| `run.sh` | Точка входа: очередь задач или проверки через `--check` |
| `orchestrator.py` | Выполнение очереди |
| `config.json` | Модели, Git, проверки, таймауты и пути |
| `TASKS.md` | Текущая очередь; изначально пуста |
| `PROGRESS.md` | Журнал и состояние; создаётся при первом завершении задачи |
| `.runtime/logs/` | Локальные логи; создаются при запуске и не коммитятся |
| `README.md`, `VALIDATION.md` | Инструкция и результаты проверки |
| `tests/` | Автоматические проверки с заглушкой Codex |
| `examples/` | Примеры задач и правил; автоматически не выполняются |

Связь с основным проектом ограничена рабочим каталогом, его Git-репозиторием,
`AGENTS.md` (если есть) и командами gate. Конфигурации приложения менять для установки
не требуется. В `.git` создаются блокировка и локальное исключение для логов;
основные файлы приложения меняются только по заданиям.

## Повседневная работа

1. Добавьте задачи в `orchestrator/TASKS.md`. В пределах текущего журнала используйте новые ID; для новой пачки выполните сброс, описанный ниже.
2. Сохраните изменения очереди коммитом.
3. Выполните `bash orchestrator/run.sh` из корня проекта.
4. Просмотрите изменения и журнал `orchestrator/PROGRESS.md`.

Выполненные задачи пропускаются. Новые запускаются по порядку секций в файле.
Задачи, которых ещё нет, не генерируются автоматически.
Пустой `orchestrator/TASKS.md` допустим: оркестратор сообщает, что работы нет.

```bash
bash orchestrator/run.sh --list             # ID, модель, сложность, статус
bash orchestrator/run.sh --dry-run          # также команды проверок и число повторов
bash orchestrator/run.sh --only DOC-1       # только эта задача
bash orchestrator/run.sh --from FIX-2       # с этой секции до конца
bash orchestrator/run.sh                    # вся невыполненная очередь
bash orchestrator/run.sh --push             # явно включить push после каждого коммита
bash orchestrator/run.sh --no-push          # явно отключить push из config/окружения
bash orchestrator/run.sh --check full       # только проверки проекта
bash orchestrator/run.sh --help             # справка по очереди и проверкам
```

`--only`, `--from` и `--mark-done` взаимоисключающие. Неизвестный ID — ошибка.
`--from` и `--only` не проверяют зависимости: выбор точки старта — решение пользователя.
`--list` и `--dry-run` не запускают Codex, gate или Git-записи, не создают журнал и логи;
они работают и без `git init`.

## Формат TASKS.md

````markdown
# Очередь

## DOC-1: Описать запуск проекта
tier: light
gate: bash orchestrator/run.sh --check full
retries: 1
```prompt
Создай docs/QUICKSTART.md с точными командами установки и запуска этого проекта.
Команды возьми из существующих конфигурационных файлов и документации.
Не меняй код приложения.
```

## FIX-2: Исправить обработку пустого ввода
tier: standard
gate: bash orchestrator/run.sh --check full
retries: 1
```prompt
Здесь опиши конкретную ошибку, ожидаемое поведение и критерии готовности.
При необходимости добавь к полному гейту проверки по типу правки из AGENTS.md.
```
````

| Элемент | Правило |
|---|---|
| Заголовок | `## ID: Название`; ID начинается с латинской буквы, затем буквы/цифры/`_`/`-` |
| Порядок | Как в файле; алфавитная/числовая сортировка не применяется |
| `tier` | `light`, `standard`, `heavy`; если отсутствует — `standard` |
| `gate` | Обязательная однострочная shell-команда или точное значение `skip` |
| `retries` | Число исправлений после провала gate, 0–20; по умолчанию 1 |
| `prompt` | Один непустой блок с оградой из трёх или более обратных кавычек либо тильд |

Метаданные должны стоять перед блоком prompt. Повтор ID/поля, неизвестное поле,
незакрытый или пустой prompt останавливают запуск **до обращения к Codex**.
Заголовки внутри prompt считаются его текстом. Если в задании нужны вложенные
блоки кода, используйте внешнюю ограду из четырёх кавычек или `~~~prompt`.
Русский текст, эмодзи, UTF-8 BOM и переводы строк CRLF поддерживаются.

Пример задания для этого проекта — `examples/TASKS.md`. Чтобы выполнить его,
перенесите согласованную секцию в рабочую очередь `orchestrator/TASKS.md`.

## Проверки

Для этого проекта используйте `gate: bash orchestrator/run.sh --check full`.
Без аргументов `run.sh` выполняет очередь. Режим `--check` запускает только проверки;
без имени профиля выбирается `full`. Он не читает очередь и конфигурацию, не требует
чистого рабочего дерева, не захватывает блокировку очереди и не выполняет Git-операции.
Такой вызов работает и внутри уже запущенного оркестратора.
Режим проверок отключает запись Python-байткода, в том числе в дочерних процессах:
создание `__pycache__` внутри защищённого каталога иначе остановило бы очередь.
Профили запускаются и вручную из любого рабочего каталога, если указать путь к скрипту:

| Профиль `run.sh --check` | Команды |
|---|---|
| `tools` | `python3 -m unittest discover -s tools/tests` |
| `orchestrator` | `python3 -m unittest discover -s orchestrator/tests` |
| `core` | `bash ./gradlew :core:test --console=plain` |
| `data` | `bash ./gradlew :app:verifyDictionaryLicenses :core:test --console=plain` |
| `android` | Компиляция debug Kotlin, `lintDebug`, компиляция `androidTest` |
| `full` (по умолчанию для `--check`) | Обе Python-серии, затем `:core:test :app:assembleDebug` |

`full` выполняет гейт перед коммитом из корневого `AGENTS.md`. Сборка debug сама
запускает `syncDictionaryAssets` и `verifyDictionaryLicenses`. Узкие профили нужны
для промежуточных проверок. Дополнительные проверки по типу задачи добавляйте явно:

```text
gate: bash orchestrator/run.sh --check full && bash orchestrator/run.sh --check android
gate: bash orchestrator/run.sh --check full && bash ./gradlew :app:assembleRelease --console=plain
```

Для UI-поведения нужен также тест на устройстве/эмуляторе согласно `AGENTS.md`.
Профиль `android` только компилирует инструментальные тесты. Скрипт сохраняет код
ошибки и прекращает выполнение при первом сбое. Отсутствующий SDK/JDK не считается
успехом: настройте окружение перед реальной очередью. Не заменяйте гейт на `skip`.
Release остаётся заблокированным до ручного аудита определений.

Далее описаны универсальные возможности настройки команд; они не заменяют
обязательные проверки проекта.

Без настройки `gate_base` команда выполняется на хосте через `sh -c` в корне проекта.

Для Docker задайте в `config.json`:

```json
"gate_base": ["docker", "compose", "run", "--rm", "app"]
```

Тогда `gate: npm test` превращается в `docker compose run --rm app sh -c 'npm test'`.
Путь, сервис и зависимости должны существовать в целевом проекте.
Весь массив `gate_base` — аргументы команды, а не строка shell: конвейеры,
перенаправления и `&&` пишите в `gate`, а не в `gate_base`.

Проверка выполняется внешним оркестратором, с правами пользователя на хосте.
Это удобно для Docker, даже если агент не может его запустить внутри своей песочницы.
Парсер поддерживает `gate: skip` для использования комплекта в других проектах:
пропуск явно записывается в журнал как **ПРОПУЩЕНА**. В «Составь слова» такой gate
запрещён правилами `AGENTS.md`, обязательный полный гейт сохраняется и для документации.

При провале gate агент получает исходную задачу, предыдущий ответ и конец лога;
его уже сделанные правки сохраняются. Используется новый `codex exec` с теми же моделью
и effort. После `retries` исправлений цикл останавливается. Ошибка запуска Codex,
неуспешный код выхода, пустой итог, таймаут Codex/gate и сбой push допускают
до `restart_retries` повторов с паузой `retry_delay`. Этот бюджет отделён от
исправлений проваленного gate. Строка `BLOCKED:` останавливает очередь без повтора.
Ни ошибка тестов, ни отсутствие SDK/JDK, ни ручной аудит не превращаются в успех.

## Конфигурация

Редактируйте `orchestrator/config.json`; неизвестные ключи отклоняются.
Другой файл можно передать как `--config path/to/config.json`.
Он должен находиться внутри проекта и быть добавлен в Git.

| Ключ | По умолчанию | Назначение |
|---|---|---|
| `tasks_file` | `orchestrator/TASKS.md` | Очередь, путь относительно корня |
| `progress_file` | `orchestrator/PROGRESS.md` | Журнал и состояние завершённых задач |
| `branch` | `auto/tasks` | Локальная ветка для работы |
| `remote` | `origin` | Remote для необязательного push |
| `push` | `true` | Выполнять push после каждой завершённой задачи |
| `codex_bin` | `codex` | Имя программы или путь к Codex CLI |
| `sandbox` | `workspace-write` | Песочница агента |
| `gate_base` | `[]` | Префикс команды проверки массивом аргументов |
| `task_timeout` | `3600` | Секунд на один запуск Codex |
| `gate_timeout` | `1800` | Секунд на один запуск gate |
| `git_timeout` | `120` | Секунд на commit и на push |
| `restart_retries` | `3` | Дополнительные запуски после сбоя Codex, пустого ответа, таймаута Codex/gate или сбоя push; 0–20 |
| `retry_delay` | `30` | Пауза между перезапусками, секунд; неотрицательное целое |
| `models` | light: `gpt-5.6-luna`; standard: `gpt-6.1-sol`; heavy: `gpt-6-astra` | Модель для каждого tier |
| `efforts` | `low` / `medium` / `high` | Усилие для light / standard / heavy |

В `models` и `efforts` используйте ключи `light`, `standard`, `heavy`.
Выберите доступные вашему аккаунту модели и поддерживаемые ими значения effort.
Указанные выше ID уже записаны в JSON и значениях по умолчанию программы.
Пустая строка вместо ID переключает соответствующий tier на модель из настроек Codex.

Для совместимости с исходным скриптом поддержаны переменные окружения:

```bash
export MODEL_LIGHT="gpt-5.6-luna"
export MODEL_STANDARD="gpt-6.1-sol"
export MODEL_HEAVY="gpt-6-astra"
export EFFORT_LIGHT=low EFFORT_STANDARD=medium EFFORT_HEAVY=high
```

Также: `TASKS_FILE`, `PROGRESS_FILE`, `BRANCH`, `REMOTE`, `CODEX_BIN`, `SANDBOX`,
`TASK_TIMEOUT`, `GATE_TIMEOUT`, `GIT_TIMEOUT`, `RESTART_RETRIES`, `RETRY_DELAY`, `NO_PUSH=1` (отключить push),
`NO_PUSH=0` (включить push), `GATE_BASE='docker compose run --rm app'`.
Пустой `GATE_BASE=''` запускает проверки на хосте.

Приоритет: аргумент `--push/--no-push` → окружение → JSON → значения по умолчанию.
Пути всегда отсчитываются от корня проекта. Пути с пробелами поддерживаются.
Ограничение формата: задачи, конфигурация и журнал — обычные пути без symlink и `..`.

## Новая пачка задач: очистить и заполнить заново

После завершения предыдущей пачки остановите все запуски оркестратора и убедитесь,
что нужные правки приложения сохранены в коммитах. Выполните из корня проекта:

```bash
printf '# Задачи\n\n' > orchestrator/TASKS.md
rm -f orchestrator/PROGRESS.md
```

Это полностью очищает очередь и удаляет её журнал завершения. Архивные файлы
и копии не создаются. Теперь запишите новые задачи в `orchestrator/TASKS.md`.
ID можно снова начинать с `P1`, `P2` и т.д., поскольку прежнего журнала больше нет.

Сохраните подготовку и запустите новую пачку:

```bash
git add -A -- orchestrator/
git commit -m "Replace task queue with a new batch"
bash orchestrator/run.sh --dry-run
bash orchestrator/run.sh
```

Новый `PROGRESS.md` создастся автоматически после первой завершённой задачи.
Без удаления старого журнала неизменённые задачи с прежними ID будут пропущены,
а изменённые задачи с теми же ID остановят запуск из-за несовпадения fingerprint.
Поэтому для полной замены пачки очищайте и очередь, и журнал.

Очистка не откатывает код приложения и не удаляет Git-коммиты предыдущей пачки.
Она сбрасывает только список задач и учёт их завершения. Локальные логи не влияют
на этот учёт. Их можно оставить либо после остановки процессов удалить отдельно
из `orchestrator/.runtime/`.

Обычно новую пачку запускают в текущей ветке задач. Если нужна отдельная ветка,
сначала выберите актуальную базовую ветку проекта, подготовьте и закоммитьте новую
очередь, затем задайте свободное имя ветки:

```bash
BRANCH=auto/batch-02 bash orchestrator/run.sh
```

Для продолжения используйте то же `BRANCH` либо запишите его в `config.json`.
Если такая ветка уже существует, сначала выберите её вручную.

## Git и журнал

- Стартуйте из корня Git-проекта с начальным коммитом, заданными именем/email и чистым
  рабочим деревом. Сохраните изменения в том числе внутри `orchestrator/`.
  Для возобновления своей незавершённой задачи допустимы её сохранённые правки
  при наличии контрольной точки.
- Скрипт создаёт `auto/tasks` от текущего HEAD. Если такая ветка уже существует,
  выберите её вручную: `git switch auto/tasks`. Автоматического перехода на старую ветку нет.
  Либо задайте другую `BRANCH`. Ветки `main` и `master` для выполнения отклоняются.
- Для каждой успешно завершённой задачи коммитятся все видимые Git изменения
  вместе с записью журнала. Отсутствие правок приложения допустимо: задача может
  закончиться коммитом только журнала, например после проверки существующего поведения.
- Строки `<!-- orchestrator:v1 ... -->` в `PROGRESS.md` — служебные записи с ID,
  fingerprint, итогом и результатом gate. Не редактируйте их вручную.
  Человекочитаемый текст журнала можно дополнять обычными абзацами.
- Повторный запуск пропускает выполненные ID. Изменение содержания завершённой задачи
  под прежним ID вызывает ошибку: создайте новую секцию с новым ID.
  Старые завершённые секции можно удалить из очереди, записи журнала сохраняются.
- После редактирования очереди сохраните её коммитом и снова запустите скрипт.
  Не редактируйте очередь, конфигурацию или проект одновременно с выполнением.
- `orchestrator/.runtime/` хранит логи каждого запуска и исключается локально через Git info/exclude;
  root `.gitignore` целевого проекта менять не требуется. Linked worktrees поддерживаются.
- Скрипт использует файловую блокировку на общий Git-репозиторий: второй оркестратор
  не стартует даже в другом linked worktree этого репозитория.
- Push включён по умолчанию (`push: true`); `--no-push` отключает его на один запуск.
  При провале push локальный коммит сохраняется,
  следующие задачи не запускаются. Исправьте доступ и выполните `git push` вручную,
  затем продолжите обычным запуском: сохранённый в контрольной точке push будет
  повторён до следующей задачи. `--no-push` позволяет явно продолжить локально.

Старый `PROGRESS.md` исходного проекта не переносится: у него нет fingerprint.
Если сохраняете старый комплект рядом, укажите для новой очереди новый `PROGRESS_FILE`.
При полной замене пачки очищайте очередь и удаляйте журнал по инструкции выше.

## Если выполнение остановилось

Перед запуском агента сохраняется атомарная локальная контрольная точка
`orchestrator/.runtime/checkpoint.json`: задача и её fingerprint, ветка, исходный
HEAD, снимок защищённых файлов, текущий этап и счётчики запусков. Данные агента
и незавершённые правки остаются на месте; reset, clean и stash не выполняются.
Контрольная точка не коммитится и удаляется после завершения задачи и push
(либо явного `--no-push`). Завершённые задачи определяются по закоммиченному журналу.

После внешнего прерывания достаточно повторить обычный запуск:

```bash
bash orchestrator/run.sh
```

Оркестратор продолжит незавершённую задачу, даже если в ней остались новые или
изменённые файлы. Агент получит исходное задание, последние итоги, ответ и лог,
а также указание изучить и сохранить полезные правки. Сбой во время gate
возобновляет проверку без нового вызова агента. При остановке во время коммита
повторяются gate и коммит; если коммит уже состоялся, он проверяется по родителю,
дереву Git и журналу и не создаётся повторно. Прерванный push повторяется отдельно.
Ошибки commit hook после устранения причины также восстанавливаются обычным запуском.

Сбой Codex, пустой ответ, таймаут и push сначала повторяются в текущем процессе.
Если CLI сообщает `try again at ...`, пауза увеличивается до указанного времени
сброса лимита (локальный часовой пояс машины). Иначе используется `retry_delay`.
После исчерпания повторов правки и контрольная точка сохраняются; новый запуск
начинает новый бюджет перезапусков. Ctrl+C/SIGTERM во время ожидания прекращают
работу, а не запускают новый повтор. Завершённый процесс или выключенный компьютер
требует нового запуска команды; отдельная системная служба не устанавливается.

Логи продолжаются в исходном каталоге `orchestrator/.runtime/logs/<UTC-время>/`:
`ID.exec.N.log`, `ID.gate.N.log`, `ID.last.md`, `ID.commit.N.log`, `ID.push.N.log`.
Новые попытки получают новые номера и не затирают логи прошлых запусков.

Автовозобновление требует ту же задачу, ветку, HEAD и неизменные защищённые файлы.
Другая задача через `--only`/`--from`, изменённый fingerprint, незнакомый коммит,
повреждённая контрольная точка и изменения защищённых путей останавливают запуск.
Сторонние правки в чистом ранее проекте без контрольной точки не подхватываются.
Не редактируйте приложение параллельно активной задаче: её сохранившиеся правки
будут переданы агенту и войдут в коммит после успешного gate.

При `BLOCKED:` сначала нужно решение владельца. Для проверенного ручного
исправления остаётся команда **в ветке задач**:

```bash
bash orchestrator/run.sh --mark-done FIX-2
```

Команда снова запускает gate и при успехе коммитит **все текущие изменения**
вместе с журналом, без вызова Codex. Используйте её только для разобранных
изменений этой задачи. Обязательный полный гейт проекта сохраняется.

Если изменены защищённые файлы, сначала восстановите их из коммита, сохранив нужные
правки приложения отдельно. Без собственной контрольной точки оркестратор
откажется использовать незакоммиченный журнал как подтверждение завершения.
Запуски старых версий без `checkpoint.json` требуют прежнего ручного разбора;
по одним логам принадлежность оставшихся правок не угадывается.

Ctrl+C, SIGTERM и таймаут останавливают активную группу процессов Codex/gate.
SIGKILL или выключение компьютера не позволяют выполнить обработчик. Дочерний
процесс наследует блокировку: пока оставшийся агент или gate ещё работает,
второй оркестратор откажется запускаться. После его завершения обычный запуск
сможет восстановиться из контрольной точки. При необходимости оставшийся процесс
следует остановить явно, сохранив правки.
Коды завершения: `0` — очередь/выбор выполнены или работы нет, `1` — ошибка выполнения
или данных, `2` — ошибка аргументов командной строки, `130` — Ctrl+C вне активного процесса.

## Границы автоматизации

Проверки контрольных сумм и Git-ветки обнаруживают случайную правку служебных файлов,
но не являются изоляцией от враждебного агента. Просматривайте diff и историю перед слиянием.
Gate — доверенная команда пользователя; она выполняется с доступом хостового пользователя.
Права агента определяются выбранной песочницей Codex; полный доступ используйте только
в подходящей изолированной среде. Настройки доверия и hooks самого Codex остаются действующими.

Оркестратор не запускает субагентов, не выполняет merge/deploy и не исправляет
Git-конфликты автоматически. Реальное качество результата зависит от постановки задачи,
правил проекта и выбранного gate. Следуйте `AGENTS.md` целевого проекта;
`examples/AGENTS.md` — лишь необязательный пример для объединения с вашими правилами.

Используемые CLI-флаги сверены с `codex-cli 0.167.0-alpha.4` (`codex exec --help`).
Запуски с настоящей моделью в проверку комплекта не входили.
Справка: https://developers.openai.com/codex/noninteractive.

## Самопроверка комплекта

Из корня целевого проекта, в который скопирован каталог `orchestrator/`:

```bash
python3 -m unittest discover -s orchestrator/tests -v
```

Тесты создают временные Git-репозитории и подменяют Codex заглушкой.
Аккаунт, API-ключ и сеть для них не нужны. Смотрите `VALIDATION.md`.
