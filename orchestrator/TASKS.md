# Финансы и FIRE — очередь исправлений UI и B4 в основной ветке `main`

> **Решение владельца, 23.11.2026:** выполнять в существующей четырёхвкладочной архитектуре `main`. Отменённый эксперимент `feature/redesign-v2` не использовать. В очередь включены 12 локальных исправлений и три задачи B4: закреплённый результат в симуляции. UI-решение B4 утверждено: слева названия, справа значения; третья строка — изменение срока; ниже счётчик и сброс. Удаление прежней сводки симуляции утверждено. В `orchestrator/config.json` ветка уже `main`; **не менять конфиг или другую часть оркестратора**.
>
> Перед работой прочитать корневой `AGENTS.md`, инструкции оркестратора и фактические Kotlin-исходники. В `AGENTS.md` зафиксирован режим release hardening, запрещающий новые функции. **Владелец явно разрешил только перечисленные здесь улучшения UI/UX (включая B4); остальные продуктовые ограничения AGENTS.md действуют.** Это разрешение НЕ распространяется на алгоритмы, формулы, пороги и правила оценок, а также на переход к трём вкладкам.
>
> **Общий контракт:** минимальные атомарные изменения; финансовое ядро и сохранённые значения не изменять, не создавать Gradle `:core`, сохранять все четыре вкладки, три ползунка, 14 сценариев, шесть языков, обе темы, три вида экспорта, `applicationId` и максимально сохранять `testTag`. Числа в примерах B4 — только иллюстрации, не тестовые результаты. Сборка и проверки — существующие `--check android`, `--check unit`; не заменять неудачный gate на более лёгкий. Приёмка производится без обязательного тестирования на физическом устройстве: автоматические unit/Compose/Robolectric-тесты, сборка, статическая проверка и проверка логики; ручные тесты Gboard/Samsung, TalkBack и на реальных устройствах не являются gate или блокирующим критерием. Не заявлять о фактически непроведённых проверках. Из задач **не менять файлы внутри `orchestrator/`**, не делать самостоятельно Git-коммиты: ими управляет оркестратор. Если блокирует противоречие, сообщить `BLOCKED` с точной причиной.
>
> **Порядок:** сначала B4 (закреплённая панель → удаление дублирующей сводки → регрессионная проверка), затем исправления ввода → сохранение UI-состояния → локали/тема/форматы/доступность → токены и типографика. Для B4 требуется использовать реальный `FireRetirementScreen`, а не макеты отменённого редизайна. `FIRE | Симуляция` прокручивается; закрепляется только результат. Верхняя `TopAppBar` и четыре пункта нижней навигации сохраняются.


> **Правило приёмки:** не создавать `BLOCKED` и не считать задачу непринятой только из-за отсутствия физического устройства, Gboard/Samsung Keyboard или TalkBack; достаточно корректного кода, воспроизводимых автоматических проверок и указанного gate. Можно отметить ограничения проверки в отчёте, но не ставить ручные проверки условием завершения.

## B4-01: Закреплённая панель: две колонки «название | значение», три строки показателей
tier: heavy
gate: bash orchestrator/run.sh --check android
retries: 1
```prompt
ЗАДАЧА: заменить прежнюю SUMMARY-верстку симуляции отдельной sticky-панелью строго по утверждённому макету. В `FireRetirementScreen.kt` непосредственно после первого `item` в `LazyColumn`, содержащего `FireSubtabSelector`, и ТОЛЬКО при `FireSubtab.SIMULATION` поставить `LazyColumn.stickyHeader` (с соответствующим Compose opt-in, если нужен); сохранить переключатель обычным `item` перед stickyHeader. НЕ применять отдельный оверлей с ручным отслеживанием скролла. Переключатель FIRE | Симуляция должен ПРОКРУЧИВАТЬСЯ и не закрепляться. При прокрутке sticky-панель занимает верх viewport ниже общей TopAppBar, контент скроллится ниже; нижние четыре таба не меняются.

КОМПОНОВКА sticky-панели:
- заголовок «Результат симуляции» (допустим компактный при прокрутке);
- СТРОГО ДВЕ КОЛОНКИ таблицы на всём блоке метрик: **левая колонка — только названия показателей**, **правая колонка — соответствующие значения**. НЕ располагать «Срок FIRE» и «Возраст FIRE» рядом в первой строке как названия двух независимых колонок.
- РОВНО ТРИ СТРОКИ таблицы сверху вниз:
  1. Левая ячейка `Срок FIRE` | правая ячейка `24 → 21,5 года`.
  2. Левая ячейка `Возраст FIRE` | правая ячейка `62 → 59,5`.
  3. Левая ячейка `Изменение срока` | правая ячейка `↓ −2,5 года` (зелёный статусный бейдж при улучшении).
- Отдельная НИЖНЯЯ УПРАВЛЯЮЩАЯ СТРОКА под таблицей: `Изменений: N` слева, `Сбросить` справа; она НЕ является третьей колонкой и НЕ смешивается со строкой «Изменение срока».
- Использовать адаптивные веса, например `Row` из двух `Column`: слева ~42–48% для названий, справа остаток для значений; внутри каждой колонки три строки одинаковой высоты и выравнивания по базовым линиям. При увеличенном шрифте обеспечить корректное построчное выравнивание и перенос, лучше строить каждую строку отдельным `Row` с двумя `Box/Column`, чтобы высота ячеек совпадала.
- Концептуальная (не числовой контракт) ASCII-схема (моноширинный текст без вложенного fenced block):
  ┌───────────────────────────────────┐
  │ Результат симуляции               │
  │ Срок FIRE         24 → 21,5 года │
  │ Возраст FIRE      62 → 59,5      │
  │ Изменение срока   ↓ −2,5 года    │
  │ ────────────────────────────────  │
  │ Изменений: 3       [Сбросить]     │
  └───────────────────────────────────┘
- Не выносить дельту `−2,5` в отдельный пункт под ДВУМЯ столбцами «Срок FIRE / Возраст FIRE»: такое расположение ОТМЕНЕНО последним решением пользователя.
Денежный поток, расходы и чистый капитал НЕ показывать в новой закреплённой панели. Не выводить дублирующие суммарные карточки. НЕ менять фактические значения уже существующих рычагов/событий.

СОСТОЯНИЯ: улучшение = срок уменьшился -> разница ОТРИЦАТЕЛЬНАЯ и позитивная ЗЕЛЁНАЯ; ухудшение = срок увеличился -> разница ПОЛОЖИТЕЛЬНАЯ и негативная КРАСНАЯ; нулевой эффект при активных изменениях -> `0 лет` с нейтральной семантикой без ложной похвалы; 0 активных изменений -> базовые значения БЕЗ стрелок `→`, подпись «Без изменений», `Изменений: 0`, disabled «Сбросить». Положительный/отрицательный финансовый статус НЕ определяется самим знаком числа; он зависит от влияния на срок FIRE. Для нечисловых статусов `REACHED_NOW`, `UNREACHABLE`, `HORIZON_EXHAUSTED`, `INVALID_AGE` текст брать из имеющихся форматтеров; недоступные разницы не вычислять; не показывать NaN/Infinity.

СЧЁТЧИК: количество включённых сценариев плюс количество ползунков, отличающихся от нуля; НЕ счётчик только чекбоксов. Отсутствие семантического воздействия при активном выборе не должно выдавать улучшение. Числа и форматы из текущих metrics/simulatedMetrics и Formatters, без ручной замены financial engine.

НЕПРОЗРАЧНОСТЬ: `stickyHeader` должен иметь на ВСЮ ширину LazyColumn непрозрачный внешний `Surface` с `MaterialTheme.colorScheme.background` (alpha=1f), включая горизонтальные поля, верхний/нижний зазор и участки снаружи скруглённых углов внутренней карточки; внутренняя панель может иметь лёгкий статусный tint, но никакой текст из прокручиваемых рычагов и сценариев не должен просвечивать сквозь подложку, углы и промежутки. Не применять `.alpha()` к внешнему фону. При необходимости использовать `clipToBounds` для прокручиваемой области и корректный z-order/elevation без повреждения касаний. Переключатель FIRE | Симуляция не sticky; при прокрутке полностью уходит вверх, панель становится непосредственно под TopAppBar. Проверь прокрутку вниз и обратно, разные размеры шрифта и обе темы.

ЦВЕТА: не перекрашивать весь фон в красный/зелёный яркой заливкой; мягкий статусный tint панели и контрастный цвет третьего пункта (SuccessGreen/AlertRed/WarningYellow). Общая оценка 6,7/10 по прежнему жёлтая. Не раскрашивать отдельные рычаги по цвету общего результата без оснований. Адаптивная высота без hardcoded 72dp, отступы/минимальный текст и TalkBack; 320dp × fontScale 1.6, 6 локалей не обрезаются. У панели `testTag("fire_sim_sticky_summary")`; сохранить существующие теги где возможно. Добавить/исправить локализованные UI-строки для третьей строки и состояния нуля.
```
